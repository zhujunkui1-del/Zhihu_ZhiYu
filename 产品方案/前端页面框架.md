## Profile 设置页功能说明

设置页以 ZhiYu18 的 `zhiyu-settings.html` 为基准，共四区：

1. **01 身份与数据源**：展示知乎账号授权状态（已授权/未授权），以及微信 / QQ / 飞书 / 钉钉 / SBTI 的注入状态与入口（去接入 / 去完成测试）。
2. **02 Agent 沟通偏好**：三个开关，**默认全部开启**：

| 开关 | 默认 | 关闭后的行为 | 建议数据字段 |
|---|---|---|---|
| 允许他人派 Agent 与我对话 | 开 | 对方只能看到人格卡与相似度，不能发起 Agent 对话 | `user.communication_prefs.allow_agent_invite` |
| 允许在「快速匹配」中展示相似度 | 开 | 不进入快速匹配候选池，不被推荐给陌生人 | `persona.visibility.show_similarity` |
| 允许对方发送匹配报告给我 | 开 | 对方不能把匹配报告发送到我的账号（通知中心不出现） | `user.communication_prefs.allow_report_delivery` |

3. **03 AI 大模型接入**：见《AI模型接入设置方案.md》；预设自动带默认模型，自定义“模型名”同时作为请求 `model`；API Key 采用服务端加密入库，延迟测试由服务端代理发起最小对话请求。
4. **04 账号与退出**：退出登录，返回登录页（含二次确认）。

### 02 区：沟通偏好的 API 契约（增量补充，2026-09）

**缺口记录**：本表下方三个开关此前只有 UI 与数据表，**没有 API 契约**，
导致实现时漏掉了读写接口——开关可以点，但没有任何东西会真正生效。
本节补齐契约，作为实现依据。

**字段名以代码为准**：数据表为 `zhiyu-web/prisma/schema.prisma` 的 `CommunicationPrefs`，
字段是**扁平的 camelCase**（上表「建议数据字段」一列写的嵌套 snake_case 属早期设想，
已作废，不要照抄）。

#### 读写接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/settings/prefs?userId=<id>` | 读取三个偏好；记录不存在时返回全 `true`（默认全开），**不隐式建行** |
| `PATCH` | `/api/settings/prefs` | 局部更新；body 只带要改的字段；记录不存在时用默认值建行后再更新 |

请求 / 响应：

```jsonc
// PATCH /api/settings/prefs
{ "userId": "user_xxx", "allowAgentInvite": false }

// 统一响应
{ "ok": true, "prefs": {
    "allowAgentInvite": true,
    "showSimilarity": true,
    "allowReportDelivery": true
} }
```

约束：

- `userId` 必填；未找到用户返回 `404`。
- 三个字段都是 `boolean`，**不接受 `null`**；未出现在 body 中的字段保持原值。
- 三个字段**默认全部为 `true`**，与数据表 `@default(true)` 一致。
- 只返回这三个字段，不返回该表其他列或用户信息。

#### 三个开关各自约束什么（实现时必须真正生效，不能只存不用）

**方向很关键**：前两个开关约束的是「**别人能不能对我做某件事**」，
所以校验的是**被访问方 / 被推荐方**的偏好，不是操作发起方的。

| 字段 | 关闭后必须在**服务端**拦截的行为 | 拦截点与校验对象 |
|---|---|---|
| `allowAgentInvite` | 他人不能对该用户发起 Agent 对话；只能看到人格卡与相似度 | `POST /api/matches/[id]/start`：在创建 `AgentSession` 之前校验**被访方**的偏好。<br>以 A 发起为例 —— 若 **B 侧用户**关闭，则拒绝；<br>反向（B 发起、A 侧关闭）同样拒绝，所以 A、B 两侧都要查。<br>该路由已 `include: { personaA: { include: { user: true } } }`，可直接取到，无需加查询。 |
| `showSimilarity` | 该用户的 Persona 不进入快速匹配候选池，不被推荐给陌生人 | `GET /api/matches/quick`：候选池查询的 `where` 中排除该用户的人设。<br>注意原型里这一项写的是 `persona.visibility.show_similarity`，<br>但落到实现是**用户级**开关（表在 `CommunicationPrefs`），不要按 persona 级去建字段。 |
| `allowReportDelivery` | 他人不能把匹配报告投递到该用户的通知中心 | `POST /api/matches/[id]/send-report`：在创建 `Notification` 之前校验**收件人**的偏好。<br>该路由已能取到 `match.personaA.userId` / `personaB.userId`，从中确定收件人。 |

> **重要 1**：三项都必须**服务端校验**，不能只靠前端隐藏按钮。
> 关闭 `showSimilarity` 是对用户的隐私承诺（"不被推荐给陌生人"），
> 仅在 UI 层处理会构成实际泄漏。
>
> **重要 2**：`allowAgentInvite` 与 `allowReportDelivery` 都不是"我自己能不能发起"，
> 而是"别人能不能对我发起"。若按发起方校验，会出现
> **关闭开关的人反而仍被别人打扰**的逻辑反转。
