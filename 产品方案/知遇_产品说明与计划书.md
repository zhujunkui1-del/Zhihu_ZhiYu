# 知遇 ZhiYu · 产品说明与计划书

> **参赛赛道**：知乎黑客松「灵魂匹配局：社区连接与兴趣社交」
> **一句话**：让 Agent 先替你认识一个人。
> **文档性质**：面向初审评定的独立说明材料，阐述创作思路、技术方案与对知乎社区的场景价值。
> **技术基线**：单体 Next.js 全栈（App Router）、部署 Vercel、数据 PostgreSQL（Neon）。
> **实现状态**：7 个页面与 20 个 API 已实现并逐项验证；知乎 OAuth 代码完整，等待部署后公网回调联调。

## 一、创作思路：我们想解决的，是"认识一个人"的成本问题

### 1.1 一个所有社区都绕不开的问题

知乎的核心价值是**连接**：让人与人因为共同的知识兴趣、观点、专业领域而相遇。

但"相遇"之后要发生什么，社区产品一直没解决好——**从"看到一个人"到"真正认识一个人"，中间那段成本极高**：

| 环节 | 现状 |
|---|---|
| 发现 | 靠时间线、推荐流、搜索，看到的是**内容**，不是**人** |
| 判断 | 只能靠几条动态、几句简介，信息量极少 |
| 试探 | 私信、评论、约聊——**试错成本高**，且多数试探以"聊不到一起"告终 |
| 结果 | 大量潜在的高价值连接，**还没开始就结束了** |

我们做了一次用户访谈式的自我代入：为什么会这样？

**因为判断"我和这个人合不合得来"，本质上需要大量信息，而人在决策前能提供的表达量太小。** 简介写不下，动态看不出，一次对话又太贵。

### 1.2 于是我们问了一个问题

> **如果 AI 已经足够了解「我」，它能不能先替我去认识对方？**

不是"AI 帮我写自我介绍"，也不是"AI 帮我筛选关键词"，而是：

**让一个真正理解我的 Agent，去和一个真正理解 TA 的 Agent 先聊一次。**

于是流程从

```
人 → 人
```

变成

```
人 → Agent → Agent → 人
```

### 1.3 三个关键判断（这是本项目的创作内核）

**判断一：匹配的目标不是"最像"，而是"最值得认识"。**

社区里最可惜的错过，往往是"观点不同但能相互启发"的两个人。
所以我们不从单一相似度排序，而是**五维加权**：

```
兴趣同频 · 思维共振 · 价值观契合 · 沟通适配 · 互补程度
```

其中「互补程度」是**反向**的：越不像，这一维越高。

> 我们的产品主张是：**真正适合认识的人，不一定是最像你的人。**

**判断二：Agent 对话不能是"自由聊天"，必须是可评估的结构化对话。**

自由聊天无法比较、无法解释、无法复现。所以每一次 Agent 匹配都**只跑固定轮次的定向提问**——围绕能够暴露兴趣、价值观与思维方式的话题，每轮由系统出题，双方 Agent 各自作答，最后交由 Judge Agent 给出五维评分与理由。

这一点直接决定了产品能不能规模化（见 §3.3）。

**判断三：人和人的关系，需要"看得见的地图"。**

技术上是"相似度 87%"，但人脑理解不了 87% 是什么概念。
所以我们做了**相遇雷达**：以"我"为中心，每个候选人的头像落在轨道上，**离我越近就越同频**。

一次看到几十个人的相对位置，而不是一张张翻卡片。点一下头像就能打开 TA 的人格卡。

### 1.4 为什么这件事现在才做得了

三个条件在这两年才同时具备：

1. **多源人格数据足够结构化**——公开表达、工作协作、生活聊天、显性自评，四类信息拼出一个人的立体画像
2. **LLM 能扮演"代理"**——不只是总结，而是能持有一个人的立场去和另一个代理对话
3. **成本下降到可接受**——LLM 只在"最后一公里"调用（见 §3.3）

## 二、产品形态：用户实际会经历什么

### 2.1 六源人格输入：把"我"交给 Agent

一个人有很多面。只用一种数据都不够准，所以我们支持六种来源，**任选其一即可开始，全部完成则理解最完整**：

| 来源 | 代表哪一面 | 我们能读出什么 |
|---|---|---|
| **知乎** | 表达的我 | 兴趣领域、长期关注话题、知识结构、观点倾向、专业领域 |
| **微信 / QQ** | 真实的我 | 表达习惯、沟通方式、熟人社交特征 |
| **飞书 / 钉钉** | 工作中的我 | 思维方式、知识结构、职业偏好 |
| **SBTI 测试** | 认识的我 | 用户主动填写的自我认知（15 个维度） |

我们刻意区分两类人格：

```
Observed Persona      行为/内容推断出来的「别人眼中的我」
Self-reported Persona 用户主动填写的「我认为我是怎样的人」
```

**数据越丰富，Agent 越像你。** 完整度按「生活私域 / 职场 / 公共 / 显性」四类来源覆盖计算，而不是简单数来源个数——因为两个生活私域来源（微信 + QQ）并不比"生活 + 职场"更有信息量。

**关于数据边界（我们的底线）**：
使用知乎数据必须由用户本人在开放平台授权，我们**只读取 OAuth 授权范围内的公开数据**，不触碰私信、不做导出、不用于授权范围外的用途。私域数据（微信 / QQ）走本地合规工具，服务端不落地原始内容。

### 2.2 生成我的 Agent

不是贴标签。我们要回答的是：

> 你为什么喜欢这些？你怎么思考问题？你习惯怎么和人交流？什么样的人会让你觉得聊得来？

### 2.3 两级匹配：先快后深

**第一级 · 快速匹配（不调用 LLM）**

用人格数据直接算分，秒级出结果。六维加权：兴趣同频、人格画像、话题重合、价值观适配、沟通适配、互补程度。

**第二级 · Agent 匹配（调用 LLM）**

对快速匹配筛出的少数候选，派 Agent 去和对方的 Agent 真实对话。

### 2.4 「让我的 Agent 先聊聊」

点击后**不跳页、不阻塞**：两个 Agent 立即转到后台开始对话，用户可以继续浏览其他人，侧栏出现脉冲小圆点提示"后台正在聊"，聊完通知用户。

> 你在做别的事，你的 Agent 在替你社交。

### 2.5 匹配报告：给出可解释的推荐

对话结束，Judge Agent 产出五维评分 + 综合分 + **推荐理由**：

```
综合匹配度 44%
兴趣同频 17%  思维共振 50%  价值观契合 72%  沟通适配 13%  互补程度 70%

为什么推荐你们认识？
· 价值观适配 72%
· 互补度 70%，可能产生思想碰撞
```

注意这个例子：**综合分不高，但理由是"互补"**——这正是我们想表达的判断一。

## 三、技术方案

### 3.1 整体架构

```
┌─────────────────────────────────────────────────┐
│  Next.js（App Router）· 单体 · Vercel            │
│                                                 │
│  Server Component ── 取数与鉴权（首屏带数据）      │
│  Client 岛屿 ────── 交互（雷达 / 筛选 / 弹窗）     │
│  Route Handlers ─── 20 个 API                    │
│  Vercel Workflows ─ 后台任务（Agent 对话）         │
└──────────────────┬──────────────────────────────┘
                   │
        ┌──────────┴──────────┐
        │  PostgreSQL (Neon)  │
        │  14 个模型 / 4 个迁移 │
        └─────────────────────┘
                   │
    ┌──────────────┼──────────────┐
    │              │              │
 知乎开放平台   用户 BYOK       平台默认
 OAuth + 用户API  大模型 Key     大模型
```

**为什么是单体**：本项目所有能力都需要服务端（密钥交换、LLM 调用、数据落库），拆成前后端双项目只会增加部署面而不增加能力。单体 Next.js 同时提供 SSR 页面与 API，一个仓库、一次部署。

### 3.2 三个核心数据结构

```text
User     一个账号
Persona  一个人的结构化人格（可被多个数据源填充）
Agent    按需实例化的对话代理（不常驻）
```

**关键设计：Agent 不常驻。** 这是规模化的前提，见 §3.3。

### 3.3 规模化：为什么不能让上亿 Agent 互相寻找

这是本项目最重要的架构判断。

**错误做法**是让每个 Agent 去和所有人逐个对话：

```
Agent 1 → 寻找 1 亿 Agent → 逐个对话   ≈ O(N²)
```

亿级规模下不可接受，而且**绝大多数 LLM 调用是浪费的**。

**我们的做法：检索，而不是全连接。**

```
1 亿 Persona Index
      ↓ 向量检索召回（ANN）
   1,000
      ↓ 快速匹配精排（规则评分，无 LLM）
    100
      ↓ 推荐
     10
      ↓ Agent 匹配（LLM 对话）
    1~3
      ↓ 输出
```

**LLM 只在最后一公里调用。** 前面的召回与精排都是向量检索 + 规则评分，成本可控。

因此我们对外**不会**说"我们拥有上亿个 Agent"，正确的表述是：

> 我们构建大规模 Persona Index，把海量人格信息结构化、向量化；
> **Agent 不常驻**，而是在用户触发深度匹配时按需实例化。

### 3.4 快速匹配算法（已实现并验证）

不调用 LLM，纯规则，因此**可解释、可复现、零成本**。

| 维度 | 算法 | 权重 |
|---|---|---|
| 兴趣同频 | Jaccard 相似度 | 0.30 |
| 人格画像 | SBTI 15 维编码的位差相似度 | 0.25 |
| 话题重合 | Jaccard | 0.15 |
| 价值观适配 | 多维数值的归一化距离 | 0.10 |
| 沟通适配 | Jaccard | 0.10 |
| 互补程度 | `100 − 人格相似度` | 0.10 |

**关键工程决策：`overall` 按"有值的维度"归一化**，而不是固定除以全部权重。

原因：冷启动用户往往只有一两个数据源，某些维度天然为空（如没做 SBTI 就没有人格相似度）。若固定除以全权重，一个只填了兴趣的用户会被系统判定为"和谁都不合"，这是**虚假的负反馈**。按可用维度归一化后，系统会诚实地表达"我只在当前有信息的维度上比较过"。

### 3.5 Agent 匹配：结构化对话 + Judge

**不是自由聊天**，而是固定轮次的定向提问：

```
第 1 轮  如果突然获得一周完全自由的时间，你会怎么安排？
第 2 轮  如果你可以重新选择一次自己的专业，你会怎么选？
第 3 轮  一个和你观点完全不同的人，你更愿意说服 TA，还是理解 TA？
...
```

每轮由系统出题 → A 的 Agent 答 → B 的 Agent 答 → 下一轮。

结束后 **Judge Agent** 输出：

```json
{
  "dimensions": { "interest": 0.17, "thinking": 0.50, "values": 0.72,
                  "communication": 0.13, "complementarity": 0.70 },
  "overall": 0.44,
  "reasons": ["价值观适配 72%", "互补度 70%，可能产生思想碰撞"],
  "summary": "综合匹配度 44%——价值观适配 72%；互补度 70%，可能产生思想碰撞。"
}
```

**我们用结构化输出 + 严格校验**（评分 clamp 到 0~1、理由限制条数、字段缺失有兜底），并且**LLM 失败时回退到确定性规则版**，同时把 `demoMode` 标记写进报告数据里——**页面会如实显示"本报告由确定性规则产生（演示模式）"，不把 Mock 结果冒充 LLM 判断**。

### 3.6 知乎数据接入（真实实现）

我们按知乎开放平台的**双凭证模型**接入：

| 场景 | `Authorization` | `X-OAuth-Token` |
|---|---|---|
| 读当前调用方本人数据 | Access Secret | 不传 |
| 代表授权用户读数据 | Access Secret | 传该用户 OAuth token |

已接入五个用户数据接口：**创作 / 关注 / 收藏夹 / 收藏夹内容 / 近期收藏**。

**技术要点（都是实测踩出来的）**：

1. **`uid` 必须无损解析。** 知乎 `uid` 是 18~19 位十进制数，超过 JavaScript 安全整数范围，直接 `JSON.parse` 会**静默舍入**（实测 `904491330657081871` → `904491330657081900`，无任何报错）。我们做文本预处理后再解析。
2. **回调参数是 `authorization_code`**（不是标准 OAuth 的 `code`），但换 token 的表单字段仍用 `code`。
3. **成功判定看 `access_token` 是否存在**，不把业务码 `20000` 当错误。
4. **`state` 严格校验**：服务端生成 → 绑定浏览器会话 → 短时有效 → 回调校验 → **原子消费**（数据库条件更新，并发重复回调只有一个成功）。
5. **`access_token` 加密落库**，浏览器只持有 HttpOnly 会话标识，**token 永不下发**。
6. **OAuth 凭证未配置时自动回退到演示登录**，站点不会因为缺配置而不可用。

### 3.7 工程完成度与验证

我们不是"写完就算"，每个关键行为都有自动化断言：

| 验证项 | 数量 | 覆盖 |
|---|---|---|
| 页面与地基 | 91 项 | 7 个页面 + 6 路由结构/主题/侧栏 |
| 接口与数据 | 38 项 | 发现页接口、16 位示例人格、匹配可用性 |
| 雷达组件 | 13 项 | 螺旋布局零重叠（穷举 1~40 人）、缩放锚点零漂移 |
| OAuth | 68 项 | 协议层 Mock、加密密钥域隔离、认证路由集成 |
| 通知与设置 | 23 项 | 开关真落库、BYOK、未读状态 |
| Agent 匹配 | 31 项 | 轮次分组、五维雷达、演示模式标注 |
| **合计** | **264 项** | **全部通过** |

其中一些断言是我们把踩过的坑固化下来的，例如：
- 雷达 1~40 人布局零重叠（早期算法在 16 人时有 7 组重叠）
- 缩放时光标下的世界坐标零漂移
- 沟通偏好开关**服务端真的落库**（此前只有 UI 没有接口，点了不生效）
- 响应体不含任何凭证（Access Secret / App Key / OAuth token）

**实现规模**：7 个页面 · 20 个 API · 14 个数据模型 · 4 个迁移 · 121 个源码文件。

## 四、对知乎社区的场景价值（本项目的落点）

这一节回答一个具体问题：**为什么这件事应该发生在知乎，而不是别处。**

### 4.1 知乎的独特优势：它的数据**天生适合**做人格匹配

不同平台的数据"含金量"完全不同：

| 平台 | 数据性质 | 适合推断 |
|---|---|---|
| 短视频 / 图片社区 | 消费行为、兴趣标签 | 喜欢什么 |
| 生活社交 | 关系链、日常 | 和谁熟 |
| **知乎** | **公开的长文本表达** | **怎么想、在意什么、专业在哪** |

知乎的核心资产是**公开的长文本表达**：回答、文章、想法。

这类数据能推断出别处推断不出的东西——**思维方式、价值取向、知识结构、观点倾向**。而这恰恰是判断"两个人是否值得认识"最关键、也最难获取的信息。

**换句话说：知乎的数据形态，天然适配"深层匹配"这件事。** 这是我们选择这个赛道、并把知乎作为核心数据源（而非可选来源之一）的根本原因。

### 4.2 具体场景价值

**场景一：把"关注关系"升级为"可认识的关系"**

知乎上有大量"单向关注"：我长期读某人的回答，认同 TA 的判断，但**没有任何契机开口**。

知遇提供了这个契机，并且**降低了开口的心理成本**——不是我去搭话，而是"我的 Agent 和 TA 的 Agent 聊过一次，结论是值得认识"。

> **价值**：把沉默的、单向的关注，转化为双向的、有理由的连接。

**场景二：找到"同领域的陌生人"**

知乎沉淀了大量垂直领域的深度用户：写经济学回答的、做工程实践的、研究历史的。
**同领域的人应该彼此认识，但他们通常不认识**——因为内容社区的推荐机制优化的是"内容触达"，不是"人的连接"。

> **价值**：从"内容分发"延伸到"人的分发"，形成领域内的连接网络。

**场景三：让"观点碰撞"成为推荐理由，而不是回避对象**

内容平台的推荐算法倾向于**同质化**（给你看你会赞同的）。
但社区最珍贵的部分恰恰是**有理有据的异见**。

我们的五维模型里，「互补程度」是反向维度，**专门给"观点不同但能相互启发"的人加分**。

> **价值**：在匹配层面主动对抗信息茧房，把"异见"从冲突源变成连接源。

**场景四：提升长文创作的连接回报**

一个用户花三小时写一篇深度回答，得到的是赞同数。
但**"这篇回答让我找到一个可以长期讨论的人"是更高价值的回报**。

知遇让长文创作**同时成为人格资产**——你写的东西越多、越深，你的 Agent 越能准确地代表你，你能匹配到的人也越合适。

> **价值**：给深度创作一个内容之外的回报：**更好的连接**。

**场景五：激活沉默的深度用户**

社区里有一类用户：**读得多、写得少**，或者在垂直领域很深但不活跃。
他们的价值被"内容互动量"这个单一指标掩盖了。

知遇用**人格完整度**而不是"发帖量"来衡量一个人，让这类用户也能被发现。

> **价值**：用新的度量维度，让被内容指标埋没的用户重新可见。

### 4.3 为什么这对知乎是"增量"而不是"分流"

我们刻意避免让产品成为"把人带离知乎"的工具：

1. **入口在知乎数据上** —— 用户要先授权知乎数据，才能得到准确的人格画像。**用得越深，越依赖知乎。**
2. **连接发生在兴趣之上** —— 匹配的起点是"你们都在讨论什么"，而不是"你们在同一个城市"。这强化的是知乎的**兴趣社区**属性。
3. **内容仍然重要** —— 用户的人格资产来自其创作。这给"多写、写深"提供了新的正反馈。
4. **不做私域替代** —— 我们的 Agent 对话是**结构化的、有限轮次的、围绕公共话题的**，不是聊天工具的替代品。它只负责"判断值不值得认识"，判断完之后，人与人去哪聊是用户自己的选择。

### 4.4 数据合规与用户权利

新兴的社交产品必须先把边界说清楚，我们的做法：

- **只读授权范围**：知乎数据只用用户本人 OAuth 授权范围内的公开内容，不触碰私信，不做导出。
- **不用于授权外用途**：人格数据只用于本产品的匹配与展示。
- **用户可控**：设置页三个开关，且**服务端真实执行**，不只是隐藏界面按钮：
  - 允许他人派 Agent 与我对话
  - 允许在「快速匹配」中展示相似度（关闭后**不进入候选池**，不被推荐给陌生人）
  - 允许对方发送匹配报告给我
- **凭证明文不进代码**：App Key / Access Secret / OAuth Token 只存在于服务端环境变量与加密存储；`access_token` 用 AES-256-GCM 加密落库，**浏览器永远拿不到**。
- **可解释**：每一条人格结论都保留出处（哪条内容推出了哪个特征），用户可以追问"你为什么这么认为"。

## 六、我们想验证的假设

最后，诚实地说明这个项目真正想验证什么。它不是"做一个交友产品"，而是想验证三个假设：

**假设一：结构化的人格信息，能否替代"大量试探性对话"？**
如果成立，认识一个人的成本会下降一个数量级。

**假设二：Agent 与 Agent 的对话，能否产出比"人看简介"更可靠的判断？**
如果成立，Agent 就不只是工具，而是**社交的代理**。

**假设三：在算法普遍追求"让你看更多"的时代，"让人更好地认识彼此"能不能成为一个可持续的产品方向？**

知遇的答案是：

> **先让你的 Agent 认识 TA 的 Agent。**
> 如果两个 Agent 聊完都觉得"这个人好像挺有意思"——
> **再由你们真正认识彼此。**
