# 多平台数据接入方案（微信 / QQ / 飞书 / 钉钉 / 知乎 / SBTI 决策记录）

> 状态：方向已确认（六源接入），尚未开发。
> 本文是对《知遇_AI_Agent_产品理解与开发规范_v2.0_Next.js_Vercel.md》第 3 章“Persona 的数据来源”的扩展，并与《微信数据获取与导入方案.md》保持一致。若后续开发时与 v2.0 开发规范出现冲突，以开发规范为准，并同步更新本文与规范相应章节。
> 配套同步：v2.0 开发规范已更新为 v2.1（第 3 / 4 / 20 / 22 / 23 / 28 / 31 章），与本文一致。

## 1. 目标与总体结论

让“知遇 ZhiYu”可以基于 **微信、QQ、飞书、钉钉、知乎、SBTI** 六类数据构建 Multi-source Persona。

**核心结论：六个来源都可以接入，但“获取动作发生在哪一层”决定它能否进入 Vercel 网页端。** 按接入形态可分为三类：

| 类别 | 来源 | 说明 |
|---|---|---|
| A. 官方授权直连（可进 Web/Vercel） | 飞书、知乎、SBTI | 走官方开放平台 API / OAuth，或产品内置生成，不依赖用户本机文件 |
| B. 本机工具导出 + 上传（Web 推荐路径） | 微信、QQ、钉钉消息 | 数据只存在于用户本机，网页端只接收用户主动上传的导出 JSON |
| C. 桌面软件版自动获取（本地能力） | 微信、QQ、钉钉消息 | 与线上平台分离，仅在知遇桌面客户端内运行，原始数据不出本机 |

一句话产品定位不变：

> 知遇是单体 Next.js 全栈应用，唯一线上部署平台是 Vercel；本地数据能力永远不部署到 Vercel，Vercel 只承载 Web / API / Workflows / PostgreSQL。

## 2. 六源接入总览矩阵

| 来源 | 人格语义 | Web 版（Vercel）可取性 | 桌面版自动获取 | 推荐取数参考 | 主要风险 |
|---|---|---|---|---|---|
| 微信 | 私域人格（生活/熟人沟通） | 只能 JSON 上传 | 可（移植 WeFlow 能力） | WeFlow、WeChatMsg/PyWxDump 系导出 JSON | 非商业许可 + 闭源二进制；同类工具持续遭 DMCA |

## 3. 各来源详细说明

### 3.1 微信（私域人格）

沿袭《微信数据获取与导入方案.md》的决策，不做修改：

- Web 版：只提供 **JSON 上传 + 导出工具指引**，不内嵌任何本地获取能力。
- 桌面版：把 WeFlow 的微信数据能力整体移植进知遇客户端，提供“手动提供 JSON”与“自动获取 JSON”两种交互。
- 自动获取链路：检测本机微信 4.x 数据目录 → 获取解密 key（进程级）→ 解密导出统一 JSON → speaker 清洗 → 蒸馏。
- 合规边界：WeFlow 为 CC BY-NC-SA 4.0 且内置三方闭源二进制，正式集成前需评估 clean-room 自研或授权路径；网页端指引措辞用“个人数据备份/导出”，不使用“破解”类表述。

### 3.2 QQ（私域人格）

**首选参考：shuakami/qq-chat-exporter（QCE，本地已存 qq-chat-exporter-master）。**

- 能力：NapCat 框架注入 + 扫码登录；可导出 **HTML / JSON / TXT / Excel**，图片、视频、表情可一并下载；跨平台（Windows / Linux / macOS Apple Silicon 预览），另有 Docker 部署形态；提供本机 Web 控制台 `http://localhost:40653/qce`。
- 生态兼容：QCE 的 **JSON / JSONL 导出已被 ChatLab 适配**，说明格式适合作为下游“蒸馏/分析”流水线输入。
- 许可证：GPL-3.0。若桌面版直接集成其代码，发行物需按 GPL 开源；**更稳妥的产品定位是“独立工具 + 输出格式对接”**，即用户在 QCE 里导出 JSON 再导入知遇。
- 网页端：只能上传 QCE 导出的 JSON；不能由 Vercel 直接读取 QQ 数据。
- 桌面版自动获取：参考 QCE 的 NapCat 路线，属于 Post-MVP 能力，需单独立项评估账号协议与风控风险。

**弃用：yfgug/QQFlow。** 仅 Windows、只导出 TXT/CSV、无 LICENSE、单次提交后无维护（2026-05），且 Debug API 注入方案脆弱，不进入任何技术选型。

### 3.3 飞书（职场人格）

**六个来源中最适合“官方 API 直连”的渠道之一，也是除知乎外唯一可进 Vercel 自动取数的消息类来源。**

- 接入方式：在飞书开放平台创建自建应用，配置 app_id / app_secret，走 OAuth 获取 user_access_token。
- 能力范围（参考 distilly 的 feishu_auto_collector 设计）：
  - 群聊：bot 在群内时，以 tenant_access_token 拉取目标成员的消息（过滤系统消息、表情包）。
  - 私聊：官方 `GET /im/v1/chats` 不返回 P2P 会话，需要以 user_access_token 向对方 open_id 发消息换取 chat_id（这是 API 限制，不是权限问题）。
  - 文档 / Wiki / 多维表格：拉取目标创建或编辑的文档内容（如有权限）。
- 必要权限 scope：`im:message`、`im:chat`，以及通讯录读取等按需开通。
- 约束：
  - 当前只适配中国区 `open.feishu.cn` / `feishu.cn`，国际版 larksuite.com 未适配。
  - user_access_token 有效期约 2 小时，需 refresh_token 刷新。
  - 外部联系人无法全量枚举，只能覆盖应用可见范围与已可见会话。
- Web 端技术形态：OAuth code → Next.js Route Handler 换取 token → 调飞书官方 API 拉取数据 → 短期清洗/蒸馏 → 入库，原始数据删除；token 只存 Vercel 环境变量或短期会话，不落浏览器。
- xiaofeixia（小飞侠）：仅作为“导出指引”候选观察对象，**不进入集成选型**——无 LICENSE、初始阶段、5 个月无更新，且只支持逐会话导出。

### 3.4 钉钉（职场人格）

- **文档 / 多维表格**：走钉钉官方 API 可以自动拉取（参考 distilly 的 dingtalk_auto_collector.py）。
- **消息**：钉钉官方 API **不支持历史消息读取**，只能通过浏览器登录态辅助采集；因此网页端不可自动，只能走“上传”或桌面辅助。
- 与飞书同理，钉钉的文档类内容可作为“思考方式 / 职业兴趣 / 价值观”证据；消息类内容暂列 B/C 类形态。

### 3.5 知乎（公共人格）

沿袭 v2.0 开发规范 §28.8 的设计：

- 接入方式：知乎开放平台 OAuth，浏览器完成授权后由 Next.js Route Handler 调知乎 Open API。
- 数据范围（黑客松联调级别）：本人 **创作内容、关注、收藏夹、近期收藏** 等授权接口。
- Web 端可行性：OAuth 回调需要公网 HTTPS 地址，Vercel 天然满足；凭证（app_id / app_key / Access Secret）严格区分，只存 Vercel Environment Variables，禁止进入浏览器端与 Git。
- 现状限制：zhihu-hackathon 当前无 PKCE / refresh token 机制，属黑客松联调级别，正式化前需补齐。
- 边界：只处理用户本人经授权授权的数据；禁止批量抓取、无授权读取或绕过 API 限制的行为。

### 3.6 SBTI（显性人格）

- 性质：不是外部“抓取”，而是**产品内置人格测试**，由用户在知遇内完成，结果直接生成 Self-reported Persona。
- 参考资产：sbti-skill（MIT）提供约 30+ 题、15 维计分、27 型 H/M/L 模板与曼哈顿匹配规则，可抽取为 JSON 题库与计分规则内置到产品；对应文件本地在 `开源项目/sbti-skill/references/questions.md`。
- 文案边界：sbti-wiki 的展示文案为 CC BY-NC-SA 且原作文案版权归原作者，演示期可参考结构，商用前需替换或取得授权。
- 人格分层：SBTI 属于“用户认为自己是怎样的人”，与聊天/内容推断出的 Observed Persona 必须区分，不可混为同一证据来源。

## 4. 统一导入链路与归一化 Schema

### 4.1 统一链路（Web）

```text
上传 JSON / OAuth 授权（飞书、知乎）
        ↓
解析与格式校验（各源适配器）
        ↓
Speaker 清洗（区分 self / other）
        ↓
归一化消息流 / 内容流
        ↓
Persona 蒸馏（对接 Distilly 一类能力）
        ↓
结构化 Persona 入库（PostgreSQL）
        ↓
原始数据删除（不留长期存储）
```

桌面版自动获取（微信/QQ/钉钉）走同一条清洗/蒸馏管线，但整段在本地执行，**只上传结构化 Persona**。

### 4.2 归一化消息 Schema（建议）

所有消息类来源（微信 / QQ / 飞书 / 钉钉）先转换为统一结构：

```json
{
  "source": "wechat | qq | feishu | dingtalk",
  "channel": {
    "type": "p2p | group",
    "id": "chat_id 或群号"
  },
  "message": {
    "id": "原始消息 id",
    "timestamp": "ISO 8601",
    "type": "text | image | file | system | sticker | ...",
    "content": "文本或占位描述"
  },
  "speaker": {
    "side": "self | other",
    "account_name": "发送者昵称/备注",
    "user_id": "发送者 uid / open_id / wxid"
  }
}
```

设计要点：

1. `speaker.side = self` 是人格的主要证据；`other` 只是理解上下文的辅助信息，**不得把别人的话当作目标用户人格**（群聊尤其要防止张冠李戴）。
2. 群聊场景需要群内成员映射，`account_name / user_id` 用于区分发言者，过滤系统消息、表情包、红包等噪声。
3. 知乎内容与飞书/钉钉文档不进入消息流，另归为“内容流”（authored content），作为兴趣 / 话题 / 思维方式 / 价值观证据。

### 4.3 各来源产物对照

| 来源 | 产物 | 进入 Persona 的证据类型 |
|---|---|---|
| 微信 / QQ | 归一化对话语料 | communication_style、thinking_style、interests、values |
| 飞书 / 钉钉消息 | 归一化对话语料 | 职场表达、协作方式、工作价值观 |
| 飞书 / 钉钉文档 | 文档文本语料 | topics、thinking_style、知识结构 |
| 知乎 | 创作/关注/收藏内容 | interests、topics、public voice、观点倾向 |
| SBTI | 结构化测试结果 | personality、values（Self-reported） |
| 全部 | sources[] / evidence[] 打标 | Persona 可解释性（对应 §26 Schema 与 §34 隐私原则） |

## 5. 与 Persona Fusion 的关系

v2.0 规范的数据来源章节（原三源模型：微信 / 知乎 / SBTI）扩展为：

```text
             用户
              │
   ┌────┬────┼────┬────┬────┐
   ↓    ↓    ↓    ↓    ↓    ↓
  微信  QQ  飞书 钉钉  知乎  SBTI
   │    │    │    │    │    │
 私域(生活) 私域/职场 职场  公共  显性
   └────┴────┴────┴────┴────┘
              ↓
        Persona Fusion
              ↓
           Persona
```

- 微信 + QQ 主要回答“生活里、熟人面前的我”；飞书 + 钉钉回答“职场里的我”；知乎回答“公开表达的我”；SBTI 回答“我自认为的我”。
- MVP 阶段的融合原则：各来源先独立蒸馏，再按规则化权重合并进统一 Persona；不同来源的表达差异本身是有用信号（如“工作 vs 生活”角色差异），但**不要在 MVP 引入复杂的 Persona 冲突消解模型**。
- 每个来源写入 `sources[]`，对应证据写入 `evidence[]`，支持 Match Report 的“为什么认为你是这样的人”解释链路。

## 6. 隐私、许可与合规要点

1. **原始数据最小化**：Web 上传版“用后即删”，桌面版默认“本地处理、只上传 Persona”。聊天原文不作为线上长期存储对象。
2. **授权边界**：只处理用户本人、本机、经用户授权的数据；知乎/飞书走官方 OAuth；微信/QQ/钉钉走“个人备份导出”语义。
3. **开源许可对照**：

| 项目 | 许可 | 知遇可用方式 |
|---|---|---|
| distilly | MIT | 可集成/改造蒸馏流水线 |
| sbti-skill | MIT | 题库与计分规则可抽取内置 |
| WeFlow | CC BY-NC-SA + 闭源二进制 | 不直接集成；仅格式参考 / 用户自行导出；商用移植需 clean-room 评估 |
| qq-chat-exporter | GPL-3.0 | 独立工具 + JSON 对接；若集成需同协议开源 |
| xiaofeixia | 无 LICENSE | 不采用 |
| sbti-wiki 文案 | CC BY-NC-SA / 原作者版权 | 演示可参考，商用前替换 |
| zhihu OAuth | 官方平台规则 | 遵守 API 授权范围与数据使用规则 |

4. **生态风险提示**：微信/QQ 类“解密导出”项目持续处于 DMCA 与下架压力下（如 r266-tech/wechat-cli 已于 2026-08 被 DMCA 封禁）。任何此类工具都定位为“用户自己运行的独立工具 + 输出文件对接”，不打包进知遇发行物、不内嵌其二进制，避免产品级法律与可用性风险。

## 7. MVP 范围与接入节奏（建议）

不追求六源同时全自动。建议按如下节奏：

### P0（Web 必做闭环）

- SBTI 测试内置（题库/计分抽为 JSON）。
- 知乎 OAuth 接入（本人创作/关注/收藏）。
- 微信 JSON 上传（含工具导出指引），跑通“上传 → 蒸馏 → Persona”演示链路。

### P1

- QQ（QCE JSON）与飞书 JSON 上传适配器。
- 飞书官方 OAuth 自动接入（消息/文档，视评审期账号准备情况）。
- 统一归一化器 + speaker 清洗 + distilly 蒸馏流水线（Web 侧）。

### P2+（Post-MVP）

- 钉钉文档 API 接入；钉钉消息浏览器辅助方案。
- 桌面版自动获取：微信（WeFlow 能力移植）、QQ（NapCat 路线参考）。
- 多源 Fusion 权重、来源置信度进入 `confidence{}`、Persona 增量更新。

### Demo 叙事建议

一个用户同时提供“生活聊天（微信/QQ）+ 职场资料（飞书/钉钉文档）+ 知乎回答 + SBTI”，对比单一来源 Persona 与 Multi-source Persona 的差异，突出“让 Agent 先替你认识一个人”的产品主张。

## 8. 待决策 / 开放问题

1. 归一化解析器部署位置：建议 Web 端只接收白名单 JSON 格式，解析/清洗在 Route Handler 或 Vercel Workflows 中执行，具体由 P0 开发确认。
2. 飞书/钉钉文档文本与媒体消息是否纳入 MVP 蒸馏范围。
3. 各来源的置信度与冲突信号如何进入 `confidence{}` 与 Match 解释。
4. 桌面客户端框架选择（Electron / Tauri）需在桌面版立项时确定，与本文解耦。
5. 环境变量命名统一：本文建议知乎凭证采用与 zhihu-hackathon skill 对齐的命名（app_key / access secret），旧文档曾出现 ZHISHU_ 前缀示例，编码时统一以 ZHIHU_ 为准；所有 Secret 只进 Vercel Environment Variables。
